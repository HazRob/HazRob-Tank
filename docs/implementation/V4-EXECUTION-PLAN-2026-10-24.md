# خطة تنفيذ HazRob Tank V4 — المرجع الموحد

**التاريخ:** 2026-10-24  
**النطاق:** مشروع **HazRob Tank المستقل فقط**: تطبيق Android (`com.hazrob.tank`)، فيرموير `ESP32-Tank`، فيرموير `Cam-tank`، وحزمة ChemCore Stable.  
**حالة الوثيقة:** أُذن بتنفيذ خطة V4 صراحةً بتاريخ **2026-10-24**. بدأ التنفيذ الفعلي على `feature/tank-v4-implementation`؛ راجع سجل الإنجاز لتحديد ما هو SOURCE_PRESENT وما لم يجتز CI/DEVICE.  
**قائمة المتطلبات المعتمدة:** [V4-UPDATE-BACKLOG-2026-10-24.md](../requirements/V4-UPDATE-BACKLOG-2026-10-24.md).  
**سجل الإنجاز القابل للاستئناف:** [V4-PROGRESS-LOG-2026-10-24.md](V4-PROGRESS-LOG-2026-10-24.md).  
**قرار دمج ChemCore والمرشحين:** [الدراسة V4-012](../requirements/V4-CHEMCORE-CANDIDATES-UX-STUDY-2026-10-24.md)، **الدمج غير معتمد بعد**.

## 1. تعليمات حاكمة

1. **لا تبدأ من نسخة V3 قديمة**: فرع العمل الموجود بالفعل هو `feature/tank-v4-implementation`، ويضم تغييرات V4 لم تجتز اعتماد البناء. افحص HEAD والفرق مع `develop` وV3، ثم أصلح الموجود قبل كتابة تنفيذ بديل. `develop` يحتوي سجل المتطلبات الموحد؛ يستمر تطوير الشيفرة في فرع V4، ولا يتم دمجه دون اجتياز بوابات الإصدار.
2. **سلامة البيانات قبل التعديل**: لا تمسح جلسات المواقع أو تجارب المطور أو لقطات V3 القديمة المخزنة، حتى لو أُزيل سجل اللقطات من واجهة V4. يجب إثبات ترحيل/فتح قاعدة البيانات بأمان ووجود نسخة احتياطية قبل أي تغيير بنيوي.
3. **مصدر القياس الآني واحد**: أحدث قرار للمستخدم هو **عملية واحدة فقط** تبدأ وتُنهى وتُحلل وتُعرض نتائجها وتقريرها، **بلا زر حفظ لقطات وبلا سجل أو اختيار لقطات سابقة**. لا تحوّلها تلقائياً إلى جلسة موقع معتمدة أو تجربة مطور.
4. **المنهج العلمي**: أبقِ بصمات MQ والمنحنيات والمعادلات اللوغاريتمية وQSPR والخوارزميات المتاحة قابلة للحساب عندما تتوافر المدخلات اللازمة. اعرض ناتج PPM المحسوب مع مستوى الدليل وعدم اليقين؛ لا تجعل عدم وجود شهادة مرجعية حاجز تشغيل حسابياً، ولا ترفعه إلى إنذار امتثال مهني بلا دليل مناسب.
5. **السلامة والتحكم**: لا تضع اختبارات قيادة حقيقية أو تفليش تلقائي في CI، ولا تُلغِ E-STOP أو منطق التوقف عند فقد الاتصال أثناء تغييرات الواجهة. فكّ الحظر عن حركة الروبوت فقط بعد اختبارات على جهاز فعلي والمجنزرات مرفوعة.
6. **الإصدارات**: تبويب `الحالة` وحده يعرض رقم إصدار التطبيق للإنسان؛ تظل `versionCode` ونسخ البروتوكولات وبيانات المصدر والمعايرة الداخلية سليمة. **لا تخلط التوقيع التجريبي بالنهائي**.
7. **الدراسة V4-012 ليست موافقة على الدمج**: لا تُزل تبويب `المرشحون` أو تنقل وظائفه نهائياً إلى ChemCore قبل موافقة المستخدم. في التنفيذ الافتراضي حافظ على الاثنين مرتبطين بنفس عملية القياس.
8. **التوثيق أولاً بأول**: بعد كل دفعة ناجحة حدّث سجل الإنجاز بفرع/commit SHA، ملفات التغيير، الاختبارات، روابط Actions، القيود، والخطوة التالية. حالة `SOURCE_PRESENT` لا تعني `CI_PASS`، و`CI_PASS` لا تعني `DEVICE_PASS` أو `RELEASE_READY`.

## 2. التدقيق الابتدائي — يجب أن تكون أول عملية في الدردشة الجديدة

- اقرأ **هذه الخطة**، **سجل الإنجاز**، **سجل متطلبات V4**، ودراسة الدمج؛ راجع تعديلات V4 الموجودة لا تضف نسخاً مكررة.
- تحقق من أحدث SHA للفرعين `feature/tank-v4-implementation` و`develop` ونتيجة أحدث تشغيل من `.github/workflows/build-tank-android-v4.yml`.
- **ملاحظة وقت إعداد الخطة:** ظهرت تغييرات حقيقية على فرع V4، منها حماية تبويب الجلسات من الأعطال، واختيار مخططات ChemCore، ونصوص قوائم سوداء؛ ومع ذلك فإن آخر التشغيلات المرئية لبناء V4 (منها [40047526874](https://github.com/HazRob/HazRob-Tank/actions/runs/40047526874)) كانت `failure`. سجلات الوظائف لم يمكن استخراجها من واجهة GitHub وقت التخطيط؛ **لا تُخمن سبب الفشل**، بل أعد تشغيل فحص قابل للمشاهدة أو اجلب سجلات Gradle/إخفاقات CI الفعلية.
- سجّل أولاً جرد `already present / missing / defective / verified` لجميع المتطلبات الـ15، مع أسماء الملفات والاختبارات. لا تقل إن التعديل مكتمل بناء على رسالة commit فقط.
- تأكد من أن workflow V4 لا ينقل اسم حزمة أو إصدار نسخة قديمة (الهدف `com.hazrob.tank` وV4)، ولا يتجاوز الاختبارات الوظيفية المطلوبة بلا بديل. لا تُظهر استثناءات الاختبارات القديمة باعتبارها نجاحاً للواجهة الجديدة.
- عالج الأصول والاعتماديات: مسار بناء Android الموروث pinned، مفاتيح توقيع المسؤول، عمل نسختَي Arduino، والمصادر المستقرة لـChemCore، دون تسريب أسرار.

## 4. تفاصيل العمل ومصفوفة الاختبارات

### الدفعة 01 — إصلاح الجلسات P0 (V4-015)
- الملفات الأساسية: `FieldSessionsTab`، `FieldSessionRepository`، `ExperimentsDb`/مخطط DB الموروث، `MainActivity.showTab()`، اختبارات V4 Sessions/Spinner.
- اختبر فتح الجلسات لأول تشغيل بلا مواقع، وبعد الترحيل، ومع مئات المواقع والجلسات، ومع تغيير القائمة سريعاً، وإعادة تشغيل Activity. لا تُجرى تحديثات Spinner متداخلة ولا تُنشأ عناوين غير صالحة؛ استثناء DB يُظهر رسالة ضمن التبويب دون إسقاط التطبيق.
- اختبر أن `APPROVED` فقط يمر إلى التقارير النهائية، مع بقاء `NEW` والمسودات محلياً وعدم رفعها.
- لا تكتفِ باختبارات source assertions؛ يلزم Logcat/stack trace للهاتف قبل وسم إصلاح crash بأنه `DEVICE_PASS`.

### الدفعتان 02–03 — تباين الواجهة والتنقل (V4-002/003/004/005/009/014)
- ضع `ColorStateList`/style/drawable موحداً لكل Spinner (الصف المختار والقائمة المنسدلة)، AlertDialog، الحقول، القوائم العربية، نص البحث، حدود التحديد، حالة التركيز/التعطيل؛ الأسود على الأبيض، والأبيض على الأحمر الداكن/الخطر فقط.
- افحص `UiKit` وكل التبويبات الرئيسية والفرعية، لا قائمة تتبع المادة وحدها. لا تحوّل بطاقات الإنذار الحمراء إلى بطاقات ذات نص أسود.
- أزل الشريط العلوي الكبير بالكامل مع الحفاظ على الاتصال ووظيفة الدخول الصحيحة؛ إن لزم مدخل للاتصال يوضع ضمن المسار المقصود دون صف جديد.
- رتّب التبويبات المرئية: **القيادة → القياسات → الجلسات → التقارير → الحالة → الإعدادات → المطور**. اختبر تغيير الترتيب في كل `tabViews` و`tabNames` وأي قيمة `selectedTab` أو مؤشر تقارير/كاميرا/صلاحيات.
- طبّق تدقيق النصوص المرئية للإصدارات في جميع الحوارات والصفحات؛ `الحالة` وحدها تعرض إصدار Android المثبّت ونسخة الفيرموير/ChemCore عند الحاجة. لا تحذف معرفات source/API أو provenance اللازمة علمياً.
- Echo: التنبيه من المسافة الصالحة وقياسات cm دون فرض حساسات IR غير مثبتة أو توقف تلقائي غير معتمد. الصوت MAX4466 لا يُسمّى dBA معايراً تلقائياً.

### الدفعتان 04–05 — محرك القياس الواحد وChemCore (V4-010/007/013)
```text
READY → ACQUIRING → FINISHING → FROZEN → ANALYZING → RESULTS_READY → REPORT_READY → COMPLETE
                       └─ ERROR/PARTIAL (بيانات حقيقية فقط)
```
- مُعرّف عملية واحد `operation_id` وطوابع زمنية فعلية ومعرّفات مصادر حقيقية. تُلتقط قياسات Rs/R0/ratio لكل MQ ورقم scan_cycle والمقدار البيئي المتوفر خلال العملية؛ **لا تُستبدل R0 الملتقطة لاحقاً بقيمة أحدث**.
- **بلا زر `حفظ لقطة فورية`، وبلا قائمة أو سجل لقطات، وبلا اختيار أو تجميع لقطات قديمة.** يحتفظ التطبيق بالنتيجة المجمدة للعملية الحالية مؤقتاً لإظهار النتائج والتقرير حتى يبدأ المستخدم عملية أخرى. لا تُحذف سجلات V3 القديمة عند ترقية التطبيق.
- تُحلل لقطة/فترة العملية المجمدة نفسها: بصمات ومنحنيات ومعادلات ونماذج ChemCore/QSPR الممكنة فقط عند توافر مدخلات حقيقية. تُظهر المرشح الأول وقائمة المرشحين ودليل كل ترشيح وPPM التقديري إن حُسب، مع فصل الاستدلال عن الإثبات الصناعي/المهني.
- **نفس `operation_id`** ينتقل بين `القياس الآني` و`ChemCore` و`المرشحون` وPDF، ولا يعود `lastMeasurementSessionId()` الخاص بجلسة ميدانية أخرى ليغيّر المرشحين.
- تدقق V4-013 نسخة **ChemCore Stable المثبتة والمعتمدة** من مصدر مرجعي موثق (hash/commit/version/count) قبل تضمينها في APK. بيانات تقنيات الـ80 غير المرقّاة علمياً ليست Stable تلقائياً. حافظ على المكتبة القديمة عند فشل تحقق الجديدة.
- انقطاع الاتصال أثناء أخذ القياسات أو نقص العينات يعرض حالة `PARTIAL/ERROR` بدقة ولا يخلق ترشيحات أو أرقاماً/أزمنة لا سند لها.

### الدفعتان 06–07 — المخططات والتقرير (V4-011/006)
- حافظ على **20 اختياراً** في `التقارير` للجلسات الميدانية المعتمدة، وأضف اختياراً مناسباً للمخططات في القياس الآني وChemCore، مع تكبير الرسم.
- رسم زمن قياس يتطلب **عينتين حقيقيتين مختلفتي الزمن على الأقل**، وبحسب متطلبات كل نوع. لا تولّد t50/t90/AUC/recovery أو تعرض منحنيات متواصلة من قراءة منفردة.
- لا تفبرك بيانات PM غير المركبة؛ الجزيئات لها تبويب فرعي مستقل. يتوافق تنسيق حقول الرسوم والقوائم مع V4-009.
- زر `📄 إصدار تقرير القياسات الآنية` يظهر في العملية الحالية؛ التقرير العربي RTL يضم timestamps ووحدات ومصادر وR0 الملتقطة وقنوات الحساسات وآلية ChemCore والترشيحات من **العملية نفسها**، ثم يحفظ عبر Android SAF. لا يمر التقرير عبر قائمة الموقع APPROVED ولا تجربة المطور.
- تحقق من PDF على عارض/هاتف Android فعلي، ومن ملف Excel الخاص بجلسات المواقع دون تغيير نطاقه. لا تستخدم صورة نمطية لتدعي أنها نتيجة حساسات.

### الدفعة 08 — نظاما التحديث والنشر (V4-008)
**أ. تحديث مستقل وآمن:** Manifest HTTPS خاص بـTank، `versionCode` تصاعدي، `applicationId=com.hazrob.tank` ثابت، شهادة توقيع دائمة ومثبتة، hash SHA-256 وتنزيل بحالات ظاهرة، SAF/Installer حسب منصة Android. بعد تثبيت تحديث حقيقي يجب استمرار المواقع والجلسات وR0 والإعدادات. برنامج ChemCore Stable له manifest/ملف/تحقق/تفعيل ذري/rollback منفصل عن APK؛ لا تُفعّل حزمة مختبرية بلا مراجعة.
**ب. رفع اختياري للمطور فقط:** لا ترفع سجلات المستخدم أو القياس الآني أو بيانات المواقع تلقائياً. أزل الوجهة القديمة `sohpany/SERVOC-Android/release/hazrob-0.10.2-rc2` من `GitHubReferencePublisher` واستبدلها بوجهة مراجعة على `HazRob/HazRob-Tank` بعد اختبار وجود الفرع وصلاحيات الكتابة. ارفع فقط العينات المعتمدة والمثبتة المصدر بعد موافقة المطور؛ سجل SHA256/commit URL/time، اقرأ المحتوى بعد رفعه للتحقق، تعامل مع 401/403/404/409/422 وتكرار الطلب والانقطاع مع صف إعادة محاولة محلي.
**ج. حماية الأسرار:** Android Keystore/آلية خدمة مصادق عليها؛ لا تلصق PAT/رمز دخول في سجلات GitHub أو النصوص أو APK. **الرفع إلى المراجعة لا يساوي ترقية ChemCore Stable.**

### الدفعة 09 — ثلاث حزم مستقلة (V4-001)
1. `HazRob-Tank-V4-ESP32-Arduino.zip`، فيه `ESP32-Tank/ESP32-Tank.ino` وجميع ملفات `.h/.cpp` المطلوبة، مع تعليمات اختيار لوحة ESP32 وتثبيت المكتبات المناسبة.
2. `HazRob-Tank-V4-ESP32-CAM-Arduino.zip`، فيه `Cam-tank/Cam-tank.ino` ومصادر الفيديو اللازمة، مع تعليمات AI Thinker ESP32-CAM/PSRAM، ودون أسرار.
3. `HazRob-Tank-V4.apk` **ملف APK مستقل** دون ZIP، وموقّع بشهادة ترقية دائمة إن توفرت؛ إذا تعذر التوقيع الدائم، يُسمى `-UNRELEASED-debug.apk` ولا يدّعى أنه الإصدار النهائي.

**تحقق الاستلام:** فكّ الضغط، فتح ملفَي `.ino` من Arduino IDE بعد الاستخراج (ليس Add ZIP Library)، تجميع فعلي للوحتين، اختبار تبعياتهما، ملفات SHA256 لكل منتج وروابط تحميل مستقلة. نبّه صراحةً إلى أي قصور NAPT/الكاميرا البعيدة أو متطلبات قبول غير منفذة.

| L3 — Android acceptance | هاتف فعلي: تبويبات/Spinner/جلسات/مخططات/PDF/Offline/upgrade/Arabic RTL + Logcat | DEVICE_PASS عند إثباته |
| L4 — Robot integration | المجنزرات مرفوعة: محركات/STOP/E-STOP/500ms/الاتصال المباشر والبعيد/Echo/MQ/ADS/BME/CAM | HARDWARE_PASS |
| L5 — Release | توقيع ثابت وتحديث دون ضياع بيانات، عدم وجود P0، ملفات منفصلة وفحوص hash | RELEASE_READY فقط |

أي فشل اختبار يجب تسجيله مع اسم السيناريو وأثره؛ لا تُحذف الاختبارات لكي يظهر CI أخضر. لا تختبر توقف المحركات أو PPM على الورق وتصفه بأنه اختبار حقيقي.

## 7. آلية استمرار العمل بعد انقطاع الاتصال

- اكتب في [سجل الإنجاز](V4-PROGRESS-LOG-2026-10-24.md) عقب كل دفعة: **رقم الدفعة، معرفات V4، SHA المصدر قبل/بعد، الملفات، المسارات المعتمدة، الاختبارات المنفذة والعدد، run ID/رابط Actions/نتيجة، ما نجح وما فشل، الملفات المخرجة وSHA256، المخاطر، الخطوة التالية**.
- استخدم `NOT_STARTED / SOURCE_PRESENT / TEST_FAIL / CI_PASS / DEVICE_PENDING / HARDWARE_PENDING / BLOCKED_EXTERNAL / RELEASE_READY`؛ لا تُخفِ الفشل أو تستخدم عبارة «تم» قبل نجاح الاختبار المستهدف.
- حدّث سجل المتطلبات فقط عند تعديل قرار المالك أو بعد قبول صريح، واحفظ إحالة أرقام البنود القديمة وفق جدول [التوفيق بين الفرعين](../requirements/V4-UPDATE-BACKLOG-2026-10-24.md).
- **لا تعدّل الشيفرة في هذه المحادثة.** في الدردشة التالية ابدأ ببناء V4 وإصلاح فشل CI والجلسات، لا تبدأ تلقائياً من الدفعة 02. إذا استؤنف التنفيذ على فرع جديد لاحقاً، يجب حفظ SHA الأصل وروابط المقارنة.
